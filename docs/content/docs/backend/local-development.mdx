# 本地开发

## 一键启动（Windows PowerShell）

在仓库根目录执行：

```powershell
.\scripts\start-local.ps1
```

脚本会：

- 使用 `.local/project-workbench-debug` 作为后端 SQLite 开发数据目录；
- 创建 `.local/cache/go-build` 和 `.local/cache/go-mod` 缓存目录；
- 首次启动时，如果 `web/node_modules` 不存在，执行 `bun install --frozen-lockfile`；
- 打开两个 PowerShell 窗口，分别运行后端和前端；
- 将前端 `/api` 请求代理到 `http://127.0.0.1:8080`。

启动后访问 [http://localhost:3000](http://localhost:3000)。后端健康检查地址是 [http://127.0.0.1:8080/api/health](http://127.0.0.1:8080/api/health)。

脚本使用固定的本地开发端口：前端 `3000`，后端 `8080`。如果端口被占用，脚本会先退出，不会关闭已有进程。请分别在两个开发窗口中按 `Ctrl+C` 停止服务。

如果 PowerShell 的执行策略阻止脚本运行，可以只对当前进程临时放行：

```powershell
Set-ExecutionPolicy -Scope Process Bypass
.\scripts\start-local.ps1
```

## 手工启动

后端：

```bash
mkdir -p .local/project-workbench-debug .local/cache/go-build .local/cache/go-mod
cd backend
CANVAS_BACKEND_ADDR=127.0.0.1:8080 \
CANVAS_BACKEND_DATA_DIR=../.local/project-workbench-debug \
GOCACHE=../.local/cache/go-build \
GOMODCACHE=../.local/cache/go-mod \
go run ./cmd/server
```

前端另开终端：

```bash
cd web
bun install --frozen-lockfile
bun run dev
```

`web/` 只使用 `bun.lock`。不要用 pnpm 或 npm 往同一套 `node_modules` 里再装一遍。

前端默认监听 `0.0.0.0:3000`，Vite 将 `/api` 和 OAuth 回调代理到 `127.0.0.1:8080`。如需修改代理目标，可设置 `VITE_API_PROXY_TARGET`。

## 时间线字幕转写（whisper.cpp）

时间线“字幕转写”由**本地 whisper.cpp server** 执行：后端将片段音频预处理为 16k mono wav 后，POST 到 `CANVAS_WHISPER_BASE_URL/inference`（whisper server 原生接口，`response_format=verbose_json`）。未配置该地址时，转写任务会立即明确失败，提示“撰写失败未配置本地转写服务”。

### 安装 whisper-server

```bash
brew install whisper-cpp
```

### 下载模型

仓库脚本将模型放在 `.local/whisper-models/`（已被 `.gitignore` 忽略）。多语言模型（含中文）用 `ggml-base.bin`（约 141MB）；网络受限时可用 aifasthub 镜像：

```bash
mkdir -p .local/whisper-models
curl -fL -o .local/whisper-models/ggml-base.bin \
  https://aifasthub.com/ggerganov/whisper.cpp/resolve/main/ggml-base.bin
```

### 启动服务

```bash
scripts/start-whisper-local.sh
```

脚本默认以 `ggml-base.bin` 监听 `127.0.0.1:8082`（`-l auto` 自动识别语言）。需要换模型或端口时：`WHISPER_MODEL=ggml-small.bin WHISPER_PORT=8083 scripts/start-whisper-local.sh`。

### 让后端指向该服务

后端不读取 `.env` 文件，环境变量必须由启动 shell 注入（在手工启动命令基础上追加）：

```bash
cd backend
CANVAS_BACKEND_DATA_DIR=../.local/project-workbench-debug \
CANVAS_WHISPER_BASE_URL=http://127.0.0.1:8082 \
go run ./cmd/server
```

### 验证

```bash
# 服务就绪：返回 200/404 即可
curl -s -o /dev/null -w '%{http_code}' http://127.0.0.1:8082/
# 冒烟：20 秒语音 → verbose_json 字幕段
curl -s -X POST http://127.0.0.1:8082/inference \
  -F 'file=@sample.wav' -F 'response_format=verbose_json'
```

## 外部客户端连接本机工作区

`beeftv` CLI 与 `beeftv mcp serve` 连接的是同一个本机工作区，凭据从环境变量读取：

| 变量 | 用途 |
| --- | --- |
| `BEEFTV_BASE_URL` | 本机工作区地址，默认 `http://127.0.0.1:8080/api`；只接受回环主机 |
| `BEEFTV_OWNER_TOKEN` | owner 凭据：可执行写操作、登记客户端；运行时会把它写到数据目录下 0600 的文件 |
| `BEEFTV_CLIENT_ID` / `BEEFTV_CLIENT_TOKEN` | 已登记客户端凭据：能力模式由服务端登记决定，不能自我提升 |
| `BEEFTV_DESKTOP_TOKEN` | 仅供桌面管理操作（如登记客户端）通过入口守卫；不要交给外部 Agent |

两条边界：

- 已登记的外部客户端只需自身凭据，即可访问同一个桌面工作区的 `/api/ops` 和 `/api/ops/:op`。它不能访问其他桌面 API、登记客户端或签发 UI 写会话。不要向外部 Agent 分发 owner 或桌面壳凭据。
- 内置 UI 通过 Wails 绑定获得独立的短期引导凭据，再签发 UI 会话；单独出示桌面启动令牌不能取得助手写会话。
- 客户端登记（`beeftv client register`）按合同需要 owner 凭据；桌面形态下同时需要桌面启动令牌。令牌值只在本机进程环境与本机 0600 文件里流转，不写入日志、不写进文档示例。

桌面发行包自带内置助手及 Node 24.15.0，无需用户安装 Node。macOS 的运行时位于 `BeefTV.app/Contents/Resources/agent-host/runtime/bin/node`，Windows 位于 `BeefTV.exe` 同级的 `agent-host/runtime/node.exe`。桌面后端直接启动随包 Node 与 `server.mjs`。

构建发行包前必须设置 `BEEFTV_NODE_RUNTIME`：macOS 指向包含 `bin/node` 的官方 Node 目录，Windows 指向包含 `node.exe` 的官方 Node 目录。运行时版本、平台或架构不匹配都会终止构建；macOS 还会拒绝依赖 Homebrew 等非系统动态库的 Node。GitHub Actions 为每个平台准备固定版本运行时。

打包脚本在临时目录使用 Bun 和 `agent-host/bun.lock` 安装冻结的 production 依赖，再以随包 Node 验证 SDK 导入。它不会复制开发目录中的 `node_modules`，也不会在缺少运行时时回退到系统 Node。两个发行入口分别为 `scripts/build-beeftv-release.sh` 和 `scripts/build-beeftv-windows-release.ps1`。

## 桌面形态与浏览器形态的身份边界

两种运行形态共用同一套 `/api` 路由，但入口门不同。用浏览器连 `cmd/server` 时按桌面的思路去找「启动令牌」一定会撞墙，所以先把层次分清楚：

| 形态 | 入口 | Profile | 入口令牌（整个 `/api`） | 操作层身份（`/api/ops*`） |
| --- | --- | --- | --- | --- |
| 桌面 | `backend/cmd/desktop` | `bootstrap.ProfileDesktop` | `X-Desktop-Token` 必须正确 | 已登记客户端 / owner / 受信任桌面界面，三选一 |
| 浏览器 + 独立服务 | `backend/cmd/server` | `ProfileServer` | 无这道门 | 同上，但「受信任桌面界面」这一路恒为假 |

### 桌面形态：入口令牌之后还有第二层身份

`backend/internal/bootstrap/runtime.go` 只在解析出的启动令牌非空时，才用 `backend/internal/transport/http/token.go` 的 `RequireLaunchToken` 包住整棵路由树（路由只挂在 `/api` 组下）。请求头常量是 `LaunchTokenHeader = "X-Desktop-Token"`，比对使用 `subtle.ConstantTimeCompare`，失败返回 HTTP 403 和 `reason=desktop_token_required`。豁免只有两类：

1. `RequireLaunchToken` 内部放行 `OPTIONS` 预检和 `GET /api/health/live`；
2. 接线处再放行「已登记外部客户端的操作层入口」：连接地址是回环、路径是 `GET /api/ops` 或 `POST /api/ops/<op>`（判据 `isOpsEntryPath`），并且 `X-Beeftv-Client` 与 `Authorization: Bearer <token>` 命中登记表。`/api/ops/clients` 属于凭据签发，不在豁免内。

令牌来源是启动环境变量 `CANVAS_DESKTOP_LAUNCH_TOKEN`（`backend/cmd/desktop/app.go`）；未设置时由 `httptransport.NewLaunchToken()` 在组合根随机生成，只存在于该进程内存。WebView 不从构建期常量取它：`DesktopApp.RuntimeConfig()` 经 Wails 绑定返回 `baseURL` / `launchToken` / `uiBootstrapToken`，`web/src/services/desktop-runtime.ts` 拿到后为 `/api` 请求补上请求头；绑定尚未就绪时退回 `GET /__desktop/runtime-config`。由桌面内置资源处理器转发的 `/api` 请求，`X-Desktop-Token` 由后端自己注入。

过了入口令牌不等于有身份。`resolveCaller`（`backend/internal/handler/agent_ops.go`）仍要求三者之一：

- 已登记客户端：`X-Beeftv-Client` + `Authorization: Bearer`；
- owner 凭据：`X-Beeftv-Owner` 等于数据目录里 `agent_owner_token` 的内容；
- 受信任桌面界面：`desktopTrust` 同时校验 `X-Desktop-Token` **和** Wails 绑定给出的 `X-Beeftv-UI-Bootstrap`，单独出示启动令牌不构成受信任界面。

三者都不满足时返回 HTTP 403、信封 `reason=forbidden`、`msg` 为「缺少可信身份：需要已登记的客户端凭据、owner 凭据或受信任的桌面界面」。因此只带正确 `X-Desktop-Token` 请求 `GET /api/ops` 仍是 403；补上 `X-Beeftv-Owner` 才得到 `code: 0`、`data.client = "owner"` 和完整操作清单。

### 浏览器 + `cmd/server`：没有入口令牌，身份判定仍在

`cmd/server` 不会传入启动令牌，`ProfileServer` 下解析出的令牌为空，入口门与 `DesktopTrust` 都不存在：

- 访问 `/api/*` 不需要 `X-Desktop-Token`；带上它也没有任何作用，不要把它当成 403 的解法。
- `/api/ops*` 依旧先过 `isLoopbackRequest`，再过 `resolveCaller`；`trustedDesktopUI` 因为 `DesktopTrust == nil` 恒为假，可走的身份只剩 owner 凭据或已登记客户端凭据。
- `requireTrustedDesktopWritePrincipal`（任务创建与重试、字幕转写、时间线渲染、深度捕捉、创作写入）在没有 `DesktopTrust` 时放行工作区 owner，但只要请求带 `X-Beeftv-Client` 就 403：外部客户端凭据在独立服务形态下不能承担这些写入口，即使同时带上启动令牌也一样。
- `BEEFTV_UI_BOOTSTRAP=1` 只改变两处判据（`backend/internal/handler/agent_clients.go` 与 `backend/internal/handler/agent_ui_session.go`）：桌面界面对外的 `/api/agent-clients*` 登记与吊销入口，以及 `POST /api/assistant/ui-session` 的签发。它不进入 `resolveCaller`，也不放松 `POST /api/ops/clients` 的 owner 要求，因此**不放开 `/api/ops`**。

### `GET /api/ops` 返回 403 时怎么定位

403 有两个互不相干的来源，先看 `msg` 再决定改哪一层：

| `msg` | 判据所在 | 该改什么 |
| --- | --- | --- |
| 「操作层只接受本机请求」「客户端登记只接受本机请求」「只接受本机同源请求」 | `isLoopbackRequest` | 来源与 Origin 放行 |
| 「缺少可信身份：需要已登记的客户端凭据、owner 凭据或受信任的桌面界面」 | `resolveCaller` | 出示 owner 或已登记客户端凭据 |

`isLoopbackRequest` 要求 `Host` 与连接地址都是回环主机，并且 Origin 满足以下之一：缺省不发；桌面已鉴权时的 `wails://wails`、`http(s)://wails.localhost`；与 `Host` **主机和端口都一致**；出现在 `BEEFTV_ALLOWED_ORIGINS` 里。仅「是回环」不算同源。

最常见的撞墙组合是：后端在 `127.0.0.1:8080`，浏览器页面在 `http://localhost:3000`，而 `web/vite.config.ts` 的 `/api` 代理带 `changeOrigin: true`，会把 `Host` 改写成 `127.0.0.1:8080`，浏览器发来的 `Origin` 仍是 `http://localhost:3000`——端口不一致即被拒。此时在启动后端时显式登记这个开发 Origin（多个用逗号分隔）：

```bash
cd backend
CANVAS_BACKEND_DATA_DIR=../.local/project-workbench-debug \
BEEFTV_ALLOWED_ORIGINS=http://localhost:3000 \
go run ./cmd/server
```

`BEEFTV_ALLOWED_ORIGINS` 与 `CANVAS_CORS_ORIGINS` 不是一件事：前者是操作层的本机同源判据，后者是 `cmd/server` 的 CORS 门。另外 `cmd/server` 的 `corsAllowedHeaders` 不包含 owner 与客户端头，所以让页面跨源直连后端并出示这两种凭据走不通。当前可行的做法是让操作层调用与页面同源（走 dev 代理），或改用不发 `Origin` 的 `curl` / `beeftv` CLI。

身份这一层，独立服务开发用 owner 通道最直接：

```bash
# 令牌值只在本机进程与终端里流转：从数据目录读取，不打印、不粘贴进任何文档或提交
OWNER=$(cat ../.local/project-workbench-debug/agent_owner_token)
curl -s http://127.0.0.1:8080/api/ops -H "X-Beeftv-Owner: ${OWNER}"
```

### owner 凭据落在哪里，怎么读

`agent_owner_token` 由 `backend/internal/agentops/clients.go` 的 `OwnerTokenPath` / `EnsureOwnerToken` 写在**后端数据目录**根下，权限 0600；首次访问操作层时按需用 `OwnerTokenMatches` 生成。两种形态都会准备这份凭据（组合根在注册路由前无条件调用 `EnsureAgentCredentials`，不按 Profile 分支），所以它的位置只取决于启动时用的数据目录，而不是某个固定绝对路径：

| 形态 | 数据目录来源 |
| --- | --- |
| 桌面发行包 | 应用自身的用户数据目录，见「桌面自动更新发布」的数据保留表 |
| 宿主机开发（`cmd/server`） | `CANVAS_BACKEND_DATA_DIR`，本仓库约定为 `.local/project-workbench-debug` |
| 未设置 `CANVAS_BACKEND_DATA_DIR` | `cmd/server` 回退到相对路径 `data` |

读取方式统一为「取当前数据目录下的 `agent_owner_token` 文件内容」：`cat "<数据目录>/agent_owner_token"`。不要把真实值写进文档、日志、issue、提交信息或浏览器 URL。它是完整工作区写权限的凭据，与「本机上能直接读该数据目录的进程」等价，因此 owner 通道是为手工界面与本机直连准备的**联调通道，不是推荐的多客户端或生产做法**。

### 多个客户端：登记客户端凭据

要让 Codex、Claude Code、Cursor 或其他 MCP 客户端连同一份工作区时，签发各自的凭据，而不是把 owner 交出去：

```bash
BEEFTV_BASE_URL=http://127.0.0.1:8080/api \
BEEFTV_OWNER_TOKEN="$(cat ../.local/project-workbench-debug/agent_owner_token)" \
beeftv client register --label dev-agent --mode read-only
```

`beeftv client register` 走 `POST /api/ops/clients`，按合同只接受 owner 凭据（`requireOwner`）；桌面形态下这条路径还额外要入口令牌，因为它不在入口豁免里。登记返回的 token 只在该次响应出现一次，服务端只保存哈希；能力模式（`read-only` / `read-write`）由服务端登记决定，请求头和请求体都不能自行提升。桌面界面的「外部 Agent」使用 `backend/internal/handler/agent_clients.go` 的入口做同一件事。只读是操作层与 MCP 的策略边界而非操作系统级隔离，完整口径见「本地 HTTP API」的只读边界一节。

### 别把来源放行当成出网放行

`BEEFTV_ALLOWED_ORIGINS` 只影响「这个请求算不算本机同源」，不会打开任何出网能力。出网侧仍默认拒绝本机、私网和链路本地上游，只能按**主机名**精确放行 `CANVAS_ALLOWED_PRIVATE_UPSTREAM_HOSTS`（见「ComfyUI 工作流」的前置条件一节）。本项目不提供「允许全部私网」这种联调绕法：上游被拒时补具体主机名，不要放开整段网段。

## 内置创作助手的本地宿主

内置助手由 `agent-host/server.mjs` 承担模型与工具循环，Go 只做运行时、业务回合与操作授权。`cmd/server` 不会传入随包运行时，因此**必须**在后端数据目录写 `agent_config.json`，否则 `/api/assistant/status` 与 `/api/assistant/chat` 都会返回 `reason=host_command_missing`：

```json
{
  "hostCommand": "C:\\Program Files\\nodejs\\node.exe",
  "hostArgs": ["D:\\path\\to\\BeefTV\\agent-host\\server.mjs"],
  "newSessionRuntime": "durable"
}
```

- 解析入口是 `backend/internal/assistantruntime/config.go` 的 `EffectiveConfig`：`hostCommand` 为空时只尝试 `BundledConfig`（桌面发行包的随包 Node 布局），独立服务形态没有这条退路。
- `newSessionRuntime` 缺省即 `durable`；填 `sdk` 才回到旧的 SDK 会话路径。
- 改这个文件或改模型渠道后，用 `POST /api/assistant/host/restart` 让后端重新拉起宿主；`agent_config.json` 只在宿主启动时读取。
- 宿主依赖必须按 `agent-host/bun.lock` 安装（lockfileVersion 2，需要 Bun 1.4.x）：`cd agent-host && bun install --frozen-lockfile`。上游升级 pi SDK 后不重装依赖，宿主会在导入阶段失败。

助手的模型选择来自工作区模型配置，两条容易踩的规则：

- `channels[].modelProfiles[].protocol` 必须是助手支持的文本协议名（`chat-completion`、`responses`、`claude-api`、`chatgpt-subscription`），写 `openai` 这类渠道格式会得到 `reason=model_protocol_unsupported`；判据在 `backend/internal/modelcatalog/assistant.go`。
- `assistantModel` 用 `<channelId>::<modelId>` 形式；留空时回退到 `textModel`。

自建推理服务需要注意上下文：助手的系统提示加 26 个操作定义约 15k tokens，`llama-server` 默认的 8192 会让每轮以 `exceed_context_size_error` 失败，信封表现为 `reason=model_error`。本地验收建议 `-c 32768`，并带 `--jinja` 才能用模型自带的工具调用模板。

### 换模型之后旧会话不可用

durable 会话的回合 checkpoint 里保存 `{provider, modelId}` 引用，恢复时用当前注册表解析；解析不到就落到 `@earendil-works/pi-durable` 的 `failNoModel`，回合表现为 `status=unanswered`、`reason=no_model`，而 `/api/assistant/status` 仍然返回 `available: true`。因此**在已有对话里更换助手模型会让该对话永久失效**，新建会话才恢复。判定方法：同模型仅重启宿主后复用旧会话正常；换模型并重启后同一会话每轮 `no_model`，同一时刻新建会话正常。

## Docker 开发

需要容器化热更新时，在仓库根目录执行：

```bash
LOCAL_UID=$(id -u) LOCAL_GID=$(id -g) \
  docker compose -f docker-compose.dev.yml up --build
```

Docker 开发编排也使用 `.local/project-workbench-debug`，并默认暴露前端 `3000` 和后端 `8080`。端口冲突时，可通过 `CANVAS_WEB_HOST_PORT` 和 `CANVAS_BACKEND_HOST_PORT` 调整宿主机端口。

### 时间线成片完整性

服务端时间线渲染需要 `ffmpeg`、`ffprobe`，字幕烧录另需 FFmpeg 的 `subtitles`（libass）滤镜和覆盖字幕字符的字体。可见的视频/图片按时间顺序拼接，真实时间空隙补黑场；独立配音和 BGM 按 `startMs` 混入，源内裁剪使用 `sourceStartMs`。视频源短于片段计划时长时保持最后一帧，音频补静音，后续片段仍按计划时间开始。音量缺省为 1，显式 0 与轨道静音必须保持静音，淡入淡出在片段时间内应用。

可见字幕烧录进 MP4，同时保留结果中的 `subtitleSrt`。缺失引用、资源不可读、音轨探测失败、独立音频无音轨、字幕滤镜或字体失败都使任务失败，不以黑场、静音或无字幕产物冒充成功。当前服务端不支持重叠的视频/图片合成，会明确拒绝；独立音轨可以重叠。

无需数据库或外部请求的本地成片验收：在 `backend/` 运行 `go test ./internal/app -run 'TestBuildRender|TestMediaResource|TestRenderContracts|TestRenderFFmpeg|TestRenderSubtitleFontFailure' -count=1 -v`。FFmpeg 集成测试生成三段共六秒素材，解码验证原声、定时配音、低音量 BGM、静音与中文字幕像素，并覆盖损坏媒体和缺字幕失败。未安装 FFmpeg/ffprobe 时该集成测试会跳过。
